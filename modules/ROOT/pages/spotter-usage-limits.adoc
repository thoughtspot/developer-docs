= Manage Spotter usage limits
:toc: true
:toclevels: 2

:page-title: Manage Spotter usage limits
:page-pageid: spotter-usage-limits
:page-description: Control and monitor the number of questions users can ask Spotter using usage pools, the Spotter usage data REST APIs, and the Visual Embed SDK.
:keywords: Spotter usage limits, usage pools, question allowance, usage counter, spotterUsageLimitConfig, upgrade workflow

Spotter usage limits allow administrators to control and monitor the number of natural language questions that users can ask Spotter. You can define usage allowances at the individual user, user group, or Org level. Spotter tracks query consumption, shows an allowance meter to end users in the embedded interface, and blocks further questions after the allowance is spent.

This page describes how to configure usage limits, choose a metering scope, configure the usage counter in the Visual Embed SDK, and build a custom upgrade workflow.

[NOTE]
====
The Spotter usage data APIs are in Beta in ThoughtSpot Cloud 26.11.0.cl. Breaking changes may be introduced before the endpoints are made Generally Available.
====

== Before you begin

Ensure you have the following setup:

* Your ThoughtSpot instance is running 26.11.0.cl or later.
* Your embedding application project has Visual Embed SDK v1.53.0 or later.
* You have a user account with `ADMINISTRATION` (**Can administer ThoughtSpot**) privilege to create and manage usage pools. `CAN_MANAGE_SPOTTER` privilege, or Org administrator privileges without cluster-level `ADMINISTRATION`, is not sufficient.

== How usage limits work
A *usage pool* is a tracked question allowance assigned to an entity: a user (`USER`), a user group (`USER_GROUP`), or an Org (`ORG`). Each pool has the following properties:

[cols="2,4", options="header"]
|===
| Field | Description
| `limit` | The maximum number of questions that the pool allows.
| `warning_limit` | The usage level at which the embedded UI shows a warning banner.
| `usage` | The cumulative number of questions consumed from the pool.
|===

You manage usage pools using the Spotter usage data REST APIs. As users ask questions in Spotter, ThoughtSpot debits the questions from the pools that apply to them and updates the usage counter in the embedded UI.

The following rules determine how pools apply to a user:

* **Allowances are additive**. +
If a user belongs to multiple groups that have usage pools, the user's effective limit is the sum of all applicable pools. For example, membership in two groups with limits of 100 and 50 results in a total limit of 150.
* **A pool without a limit makes the user unlimited**. +
If any pool that applies to a user has no `limit`, the user is treated as unlimited (`has_unlimited_pool: true`). ThoughtSpot does not debit questions for the user and does not calculate a remaining balance.
* **Usage limits are opt-in**. +
A user who does not map to any usage pool is not metered and can use Spotter without a limit.

== Choose a metering scope
A cluster supports exactly one metering scope at a time. The first usage pool created on a cluster sets its `entity_type`, and all subsequent pools must use the same `entity_type`. To change the metering scope, you must first delete all existing pools.

[cols="1,2,3", options="header"]
|===
| Metering scope (`entity_type`) | How the allowance is evaluated | Recommended use case
| `USER`
| Per individual user account.
| Personalized usage quotas, or individual user seat management.

| `USER_GROUP`
| Across all groups that a user belongs to, including inherited groups.
| Plan tier packaging, such as Trial, Standard, and Premium, or team-level caps.

| `ORG`
| Against the user's current active Org.
| Multi-tenant deployments in which Orgs purchase shared query pools.
|===

[NOTE]
====
For the `ORG` scope, `entity_identifier` is the numeric Org ID expressed as a string. For example, `"0"` represents the Primary Org.
====

== Get started

=== Create a usage pool
Send a `POST` request to the `/api/rest/2.0/ai/usage-data/update` endpoint to create a usage pool. The following example creates a pool for a user group, for example, Trial users:

[source,cURL]
----
curl -X POST \
  --url 'https://{ThoughtSpot-Host}/api/rest/2.0/ai/usage-data/update'  \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer {AUTH_TOKEN}' \
  --data-raw '{
  "updates": [
    {
      "key": {
        "entity_type": "USER_GROUP",
        "entity_identifier": "{group-guid}"
      },
      "limit": 50,
      "warning_limit": 40
    }
  ]
}'
----

=== Enable usage limits in the embed
To enable usage tracking and show the usage counter in your embedded Spotter interface, use the `spotterUsageLimitConfig` object:

[source,JavaScript]
----
import { SpotterEmbed, SpotterUsageCounterDisplayMode } from '@thoughtspot/visual-embed-sdk';

const embed = new SpotterEmbed('#tsEmbed', {
  worksheetId: '<model-guid>',
  spotterUsageLimitConfig: {
    isEnabled: true,
    usageCounterDisplayMode: SpotterUsageCounterDisplayMode.AlwaysVisible,
  },
});

embed.render();
----

For more information about the configuration options, see <<_configure_the_usage_counter,Configure the usage counter>>.

=== Retrieve the usage status of a user
To check the current usage position of a user, send a `GET` request to the `/api/rest/2.0/ai/usage-data/user` endpoint:

[source,cURL]
----
curl -X GET -G \
  --url 'https://{ThoughtSpot-Host}/api/rest/2.0/ai/usage-data/user'  \
  -H 'Accept: application/json' \
  -H 'Authorization: Bearer {AUTH_TOKEN}' \
  --data-urlencode 'user_identifier={user-guid}'
----

If you omit `user_identifier`, the API returns the usage of the authenticated user. The response includes the pools that the user draws from and the combined totals, such as `total_usage`, `total_limit`, `total_remaining`, `is_at_warning`, `is_at_limit`, and `has_unlimited_pool`.

== Manage usage pools using REST APIs
You manage usage pools using the following REST API v2.0 endpoints:

[cols="3,1,3", options="header"]
|===
| Endpoint | Method | Purpose
| `/api/rest/2.0/ai/usage-data/user` | GET | Retrieve the evaluated usage status of a user.
| `/api/rest/2.0/ai/usage-data/search` | POST | Query existing usage pools.
| `/api/rest/2.0/ai/usage-data/update` | POST | Create, update, or reset usage pools.
| `/api/rest/2.0/ai/usage-data/delete` | POST | Delete usage pools.
|===

Each pool is identified by a key that contains an `entity_type` (`USER`, `USER_GROUP`, or `ORG`) and an `entity_identifier` (the GUID of the user or user group, or the ID of the Org).

The following behaviors apply to the endpoints:

* **Partial updates**. +
Fields that you omit from an update retain their existing values. For example, updating `limit` without specifying `usage` preserves the number of questions consumed.
* **Resetting usage**. +
Pass `"usage": 0` to reset the questions consumed, for example, at the start of a new billing cycle.
* **Removing a limit**. +
You cannot remove a limit from an existing pool using an update. To make a pool unlimited, delete the pool and recreate it without a `limit`.
* **Searching pools**. +
Omit `keys` to return all pools configured on the cluster. Keys that do not match an existing pool are ignored.
* **Deleting pools**. +
Pool deletion is permanent. If you recreate a deleted pool, its usage restarts from `0`. Users who no longer draw from any pool are not metered.

For the request and response details of each endpoint, see xref:spotter-usage-data-api.adoc[Spotter usage data APIs].

== Configure the usage counter
The `spotterUsageLimitConfig` object is available in `SpotterEmbed` and `AppEmbed` in Visual Embed SDK v1.53.0 and later.

[source,JavaScript]
----
const embed = new SpotterEmbed('#tsEmbed', {
  spotterUsageLimitConfig: {
    isEnabled: true,
    usageCounterDisplayMode: SpotterUsageCounterDisplayMode.VisibleAfterWarning,
    isUpgradeButtonVisible: true,
    isWarningBannerEnabled: true,
    isLimitBannerEnabled: true,
  },
});
----

[cols="2,1,1,4", options="header"]
|===
| Property | Type | Default | Description
| `isEnabled` | Boolean | `false` | Enables Spotter usage limit enforcement and display elements.
| `isUpgradeButtonVisible` | Boolean | `true` | Controls the visibility of the *Upgrade* button in the embedded UI.
| `isWarningBannerEnabled` | Boolean | `true` | Shows a warning banner when usage reaches `warning_limit`.
| `isLimitBannerEnabled` | Boolean | `true` | Shows a notification banner when usage reaches `limit`.
| `usageCounterDisplayMode` | Enum | `AlwaysVisible` | Determines when the usage counter is displayed.
|===

[NOTE]
====
Disabling `isLimitBannerEnabled` hides the notification banner, but it does not bypass query blocking. Users cannot ask more questions after the limit is reached.
====

The `usageCounterDisplayMode` property accepts the following `SpotterUsageCounterDisplayMode` values:

* `AlwaysVisible`: The counter is always displayed.
* `AlwaysHidden`: The counter is always hidden.
* `VisibleAfterWarning`: The counter appears only after usage reaches the warning threshold.
* `VisibleAfterLimit`: The counter appears only after usage reaches the limit.

For the complete list of attributes, see xref:SpotterEmbedViewConfig.adoc[SpotterEmbedViewConfig].

== Handle usage limit events

=== Upgrade event
When an end user clicks the *Upgrade* button in the embedded Spotter interface, the embed emits the `EmbedEvent.SpotterUsageLimitUpgrade` event. Register a handler for this event to start your own upgrade flow. The event payload includes the following properties:

* `payload.data.usageCount` (__number__): Total questions asked across sessions.
* `payload.data.usageLimit` (__number__): Total assigned usage limit.
* `payload.data.status` (__string__): One of `withinLimit`, `almostReached`, or `limitReached`.

[source,JavaScript]
----
embed.on(EmbedEvent.SpotterUsageLimitUpgrade, (payload) => {
  console.log(payload.data.usageCount, payload.data.usageLimit, payload.data.status);
});
----

=== Refresh usage data
To refresh the usage data in the embed without reloading the page, for example, after a tier upgrade, trigger the `HostEvent.SpotterRefreshUsageLimit` event:

[source,JavaScript]
----
// Refresh the current usage data
embed.trigger(HostEvent.SpotterRefreshUsageLimit);

// Refresh and override settings for the current session
embed.trigger(HostEvent.SpotterRefreshUsageLimit, {
  isUpgradeButtonVisible: false,
  isUnlimited: true,
});
----

The event accepts the following optional session overrides:

* `isUnlimited`: When set to `true`, temporarily hides the usage tracking UI for the session.
* `isUpgradeButtonVisible`: Overrides the visibility of the *Upgrade* button for the session.

For a complete list of event IDs, see xref:EmbedEvent.adoc[EmbedEvent reference] and xref:HostEvent.adoc[HostEvent reference].

== Build an upgrade workflow
ThoughtSpot does not handle subscription billing. To let users upgrade their allowance, coordinate the following components: the Visual Embed SDK, your host application, your billing service, and the ThoughtSpot REST APIs.

. The end user reaches an allowance threshold and clicks *Upgrade* in the embedded interface.
. Your host application receives the `EmbedEvent.SpotterUsageLimitUpgrade` event.
. Your host application runs its own upgrade logic, for example, opening a payment dialog or changing the account plan.
. After the payment or account change succeeds, your backend calls the `POST /api/rest/2.0/ai/usage-data/update` endpoint with server-side credentials, or reassigns the user's group memberships.
. Your host application triggers `HostEvent.SpotterRefreshUsageLimit` to refresh the embed state without a page reload.

The following example shows the flow in the host application:

[source,JavaScript]
----
embed.on(EmbedEvent.SpotterUsageLimitUpgrade, async ({ data }) => {
  // 1. Process the upgrade in your billing application
  const isUpgraded = await myApplicationBillingFlow({
    currentUsage: data.usageCount,
    currentLimit: data.usageLimit,
  });

  if (!isUpgraded) return;

  // 2. Call your backend endpoint, which securely calls the ThoughtSpot REST API update endpoint
  await fetch('/api/thoughtspot/upgrade-quota', { method: 'POST' });

  // 3. Refresh the usage state in the embed
  embed.trigger(HostEvent.SpotterRefreshUsageLimit, {
    isUpgradeButtonVisible: false, // Hide the Upgrade button after a successful upgrade
  });
});
----

[IMPORTANT]
====
Do not call the usage data update endpoint from client-side code. The endpoint requires cluster-level `ADMINISTRATION` privilege, so run it from your backend.
====

== Common operational tasks

[cols="2,4", options="header"]
|===
| Task | How to
| Reset usage for a new billing cycle
| Send a `POST` request to `/api/rest/2.0/ai/usage-data/update` for each pool with `"usage": 0`. Omit `limit` to preserve the existing limit.

| Exempt a user in a group-metered cluster
| Metering is per user group in this case, so a pool of `USER` type can't be created. Instead, create a pool for the exempted user without a `limit` attribute. A user with an unlimited pool is treated as unlimited, which overrides the group-level caps. Use this approach only if the cluster scope allows the pool type.

| Audit the allowances of a user
| Send a `GET` request to `/api/rest/2.0/ai/usage-data/user?user_identifier={user-guid}` and review the `pools` array to see every contributing entity and the remaining balance.

| Change the metering scope
| Send a `POST` request to `/api/rest/2.0/ai/usage-data/delete` with all pool keys on the cluster, and then create new pools with the new `entity_type`.
|===

== Troubleshooting

[cols="2,3,4", options="header"]
|===
| Symptom | Cause | Resolution
| A user receives a higher limit than intended
| Allowances are cumulative across all pools that apply to the user.
| Review the `pools` array in the `GET /api/rest/2.0/ai/usage-data/user` response to verify group memberships, and remove unintended assignments.

| Usage is not metered for a user
| The user draws from an unlimited pool, or the assigned pools do not match the active `entity_type` of the cluster.
| Ensure all pool keys use the metering scope of the cluster, and verify that `has_unlimited_pool` is `false`.

| The usage counter does not appear in the embed
| The configuration is missing, the display mode threshold is not met, or the SDK version is earlier than 1.53.0.
| Ensure that the SDK version is 1.53.0 or later, `isEnabled` is `true`, the display mode criteria are met, and the user maps to a valid pool.

| HTTP 403 Forbidden on REST API calls
| The token does not have the required cluster-level privileges.
| Use a token for a user with cluster-level `ADMINISTRATION` privilege. `CAN_MANAGE_SPOTTER` is not sufficient.

| HTTP 400 Bad Request on update
| The request uses an `entity_type` that differs from the one set by the existing pools on the cluster.
| Use the `entity_type` that the existing pools on the cluster use.

| The counter does not change after an upgrade
| The embed state was not refreshed after the API update.
| Trigger `HostEvent.SpotterRefreshUsageLimit` immediately after the server-side update.
|===

== Limitations

* **No administration UI**. +
You can manage usage pools only using the REST APIs. ThoughtSpot Cloud does not provide a UI for pool management.
* **Beta REST APIs**. +
The endpoints may change before they become Generally Available.
* **Manual reset cycle**. +
ThoughtSpot does not support automatic scheduled resets, such as monthly resets. Use an external scheduler or a backend job that calls the REST API.
* **Single metering scope per cluster**. +
Switching between the `USER`, `USER_GROUP`, and `ORG` scopes requires you to delete all active pools on the cluster.
* **Shared pool consumption**. +
In group or Org metering, any member can consume the shared allowance. Per-user sub-caps and rate limits within shared pools are not supported.
* **Multi-Org contexts**. +
With the `ORG` scope, users who belong to multiple Orgs have a separate usage context for each Org, and draw from each Org pool independently as they switch Orgs.
