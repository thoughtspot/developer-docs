TEMPLATE GUIDE
==============
How to use this template:
  1. Copy this file from modules/_templates/release-notes-weekly.adoc.
  2. Rename the copy to <file-name>.adoc (lowercase, hyphen-separated).
  3. Place the file in modules/ROOT/pages/.
  4. If this page will be included as a partial inside another page (via include::),
     remove all front-matter attributes — partials do not need them.

Use this template for SDK changelog / weekly-patch release pages — pages
that publish frequent, incremental updates grouped by date. For monthly TSE
release notes / What's New pages, use modules/_templates/release-notes.adoc
instead; that template's table + filter + Show more behavior is reused here
too (see below), but the page-level structure differs.

Page structure:
  = Release Notes                              <- top-level heading, keep exactly as-is
  == <Version/date heading>                    <- repeat per release, newest first
    === New features and enhancements
    === Improvements
    === Action Required
    === Breaking Changes

Version/date heading:
  One `==` heading per release, ordered newest-first (matches the existing
  convention in api-changelog.adoc and mcp-server-changelog.adoc). Include
  the version and the date range it covers, for example:
    == v1.51.1 (Aug 5–26, 2026)

Table structure (applies to every subsection that has content):
  Each subsection is its own table with a header row:
    | Description | Product | Feature category
  Tag it with the `release-notes-table` role — this is the SAME role used
  by the TSE release-notes template, so it gets the same behavior for free,
  site-wide, via src/components/Document/helper.tsx + index.scss:
    - A single filter bar, rendered once above all the dated release
      sections on the page (not per table), with a "Breaking changes only"
      toggle plus Product and Feature category dropdowns. Selecting a
      filter hides non-matching rows across every table on the page, and
      collapses a whole date or subsection once nothing in it matches.
    - Automatic "Show more" for any Description cell taller than one line —
      the overflow is clipped and blurred, and the "Show more"/"Show less"
      button itself only appears when the cell is hovered or focused.
  Do not hand-roll a filter UI or a collapsible block in the .adoc source.
    [.release-notes-table, cols="3,1,1"]
    |===
    | Description | Product | Feature category
    ...
    |===
  One row per change — do not bundle multiple changes into a single cell.
  Use `a|` on the Description cell so it can hold multiple paragraphs
  (main description, an italic "Why it matters" line, and the doc
  reference line).

  Readers never see the Product or Feature category columns — index.scss
  hides everything but Description. Author them as normal table columns
  anyway; the filter bar reads its Product/Category values straight from
  those (hidden) cells, so the data still has to be there per row, it's
  just not printed as a visible label.

Product column:
  Fixed, org-wide taxonomy — always use exactly one of these four values,
  spelled exactly as shown, so the page-level Product filter works
  consistently across every release-notes page:
    ThoughtSpot Cloud | ThoughtSpot Embedded | Analyst Studio | APIs and SDK

Feature category column:
  Same convention as the TSE template — short, consistent labels reused
  across releases (for example: "Spotter", "Liveboard", "Embed SDK"). Unlike
  Product, this list is open-ended and grows with the product surface.

Doc reference placeholder:
  End each Description cell with a doc-reference line. SDK changelog entries
  often link straight to a TypeDoc symbol page rather than an internal xref:
    *Doc reference*: link:<https://developers.thoughtspot.com/docs/typedoc/...>[<Symbol name>]
  or, once an internal page exists:
    *Doc reference*: xref:<page>.adoc[<Page title>]
  If no target exists yet, leave it as:
    *Doc reference*: <Add link once this page is published>

Section rules (per version/date heading):
  === New features and enhancements — REQUIRED. If the release has none,
      remove the table and replace it with a plain sentence instead of an
      empty table or a "None" row, for example: "This release does not
      introduce any new features or enhancements."
  === Improvements                  — REQUIRED. Same empty-state rule, for
      example: "This release does not include any improvements."
  === Action Required               — OPTIONAL. Omit the entire subsection
      (heading + table) when there's nothing to act on for this release.
  === Breaking Changes              — OPTIONAL. Omit the entire subsection
      (heading + table) when the release introduces no breaking changes.
  Feel free to adjust the required sections' empty-state wording slightly,
  as long as it clearly states the section has nothing to report.

Inline badges (append after a feature name or inside a description):
  [beta betaBackground]^Beta^   — feature is in Beta
  [.version-badge.new]#New# — new in this version
  [.version-badge.breaking]#Breaking#   — breaking change
  [.version-badge.deprecated]#Deprecated#—item is deprecated
  [.version-badge.fixed]#Fixed# — bug fix

== v1.51.1 (Aug 5–26, 2026)

=== New features and enhancements

[.release-notes-table, cols="3,1,1"]
|===
| Description | Product | Feature category

a|
New `liveboardGutter` view config prop sets the pixel gap between
visualization tiles in an embedded Liveboard grid, including `0` to remove
it entirely.

_Why it matters: gives embedders pixel-level control over Liveboard density
instead of inheriting whatever gutter is saved in the Liveboard's own
styling._

*Doc reference*: link:https://developers.thoughtspot.com/docs/typedoc/interfaces/LiveboardAppEmbedViewConfig.html#liveboardGutter[LiveboardAppEmbedViewConfig.liveboardGutter]
| APIs and SDK
| Liveboard

a|
New `isLiveboardAlwaysOn12ColLayout` view config flag forces the wider
12-column grid regardless of the Liveboard's saved layout setting.

*Doc reference*: link:https://developers.thoughtspot.com/docs/typedoc/interfaces/LiveboardAppEmbedViewConfig.html#isLiveboardAlwaysOn12ColLayout[LiveboardAppEmbedViewConfig.isLiveboardAlwaysOn12ColLayout]
| APIs and SDK
| Liveboard

a|
New `Action.SpotterOnLiveboard` (for hiding/disabling the button) and
`openSpotterOnLiveboardByDefault` on `spotterChatConfig` (to control whether
it opens by default) for the Spotter button on the Liveboard header.

_Why it matters: TSEs can now control whether Spotter is reachable directly
from a Liveboard, not just from Search._

*Doc reference*: link:https://developers.thoughtspot.com/docs/typedoc/enums/Action.html#SpotterOnLiveboard[Action.SpotterOnLiveboard]
| APIs and SDK
| Spotter

a|
New `Page.LiveboardSchedules` enum value for full app embed provides a deep
link straight to the Liveboard schedules listing.

*Doc reference*: link:https://developers.thoughtspot.com/docs/typedoc/enums/Page.html#LiveboardSchedules[Page.LiveboardSchedules]
| APIs and SDK
| Liveboard
|===

=== Improvements

[.release-notes-table, cols="3,1,1"]
|===
| Description | Product | Feature category

a|
Full-height embeds now lazy-load by default — the iframe defers loading
until it's within 500px of the viewport, controlled by the existing
`lazyLoadingMargin` config.

*Doc reference*: link:https://developers.thoughtspot.com/docs/typedoc/interfaces/AppViewConfig.html#lazyLoadingMargin[AppViewConfig.lazyLoadingMargin]
| APIs and SDK
| Embed SDK

a|
Fixed a stray top gap on pre-rendered Liveboards when `preRenderContainer`
is supplied — positioning now correctly inherits from the component that
owns the pre-render, and a component that isn't the owner gets a console
warning instead of double-applying positioning.

*Doc reference*: link:https://developers.thoughtspot.com/docs/typedoc/interfaces/PreRenderConfig.html#preRenderContainer[PreRenderConfig.preRenderContainer]
| APIs and SDK
| Liveboard

a|
Fixed a visible flicker when a pre-rendered Liveboard is swapped into its
visible container.
| APIs and SDK
| Liveboard
|===

=== Action Required

[.release-notes-table, cols="3,1,1"]
|===
| Description | Product | Feature category

a|
`HostEvent.UpdatePersonalizedView` / `UpdatePersonalisedView` is now formally
deprecated, targeted for removal in SDK 1.53.0 / ThoughtSpot 26.10.0.cl.
Migrate to `HostEvent.SelectPersonalizedView`, which also accepts a
`viewName`, resets to the original view on an empty payload, and reports an
error when a named view isn't found.

*Doc reference*: link:https://developers.thoughtspot.com/docs/typedoc/enums/HostEvent.html#SelectPersonalizedView[HostEvent.SelectPersonalizedView]
| APIs and SDK
| Liveboard
|===
