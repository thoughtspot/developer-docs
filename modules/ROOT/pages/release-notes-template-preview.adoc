TEMPLATE GUIDE
==============
How to use this template:
  1. Copy this file from modules/_templates/release-notes.adoc.
  2. Rename the copy to <file-name>.adoc (lowercase, hyphen-separated, for example, "release-notes-26-5.adoc").
  3. Place the file in modules/ROOT/pages/.
  4. If this page will be included as a partial inside another page (via include::),
     remove all front-matter attributes — partials do not need them.

Use this template for release note pages (What's New, changelogs, version history).
Base format: one two-column table per section, one row per change.

Section labels:
  REQUIRED — must be present on every release note page
  RECOMMENDED — include unless there is a clear reason not to
  OPTIONAL — include only when relevant to this release

Table structure (applies to New features, Improvements, and Breaking changes):
  Each section is its own table with a header row:
    | Description | Feature category
  One row per change — do not bundle multiple changes into a single cell.
  Tag the table with the `release-notes-table` role, for example:
    [.release-notes-table, cols="4,1"]
    |===
  That role is what wires up the category filter and the per-row
  "Show more" toggle (see below) — both are handled site-wide by
  src/components/Document/helper.tsx + index.scss, driven off this class.
  Do not hand-roll a filter UI or a collapsible block in the .adoc source.
  Use `a|` on the Description cell so it can hold multiple paragraphs, code
  spans, and the doc-reference line.

Feature category column:
  Give each row a short, consistent category label (for example: "Spotter",
  "Liveboard", "Filters and parameters", "Embed SDK", "REST API"). Reuse the
  same label text across pages/releases for the same feature area — the
  `release-notes-table` role reads these values to build a filter dropdown
  (a funnel icon in the "Feature category" header, opening a vertical list
  of "All" + each category) automatically. The dropdown only appears once a
  table has 2+ distinct category values.

Doc reference placeholder:
  End each Description cell with a doc-reference line, for example:
    *Doc reference*: xref:<page>.adoc[<Page title>]
  If the target page isn't published yet, leave it as:
    *Doc reference*: <Add xref once this page is published>
  This may eventually be auto-generated from xref/page metadata; until then,
  add it by hand.

Show more / overflow content:
  Just write the description normally — don't manually split it or wrap
  anything in a collapsible block. Any Description cell taller than ~3 lines
  automatically gets a "Show more"/"Show less" toggle at render time (same
  clip + fade behavior as long code blocks), because the table has the
  `release-notes-table` role.

Improvements section:
  OPTIONAL. If the release has no improvements, remove the entire section
  (heading + table). Do not leave an empty table or a "None" row.

Breaking changes section:
  REQUIRED on every release note page, even when there are none. If the
  release introduces no breaking changes, keep the heading and table but
  reduce it to a single row reading "None" in the Description column.

Inline badges (append after a feature name or inside a description):
  [beta betaBackground]^Beta^   — feature is in Beta
  [.version-badge.new]#New# — new in this version
  [.version-badge.breaking]#Breaking#   — breaking change
  [.version-badge.deprecated]#Deprecated#—item is deprecated
  [.version-badge.fixed]#Fixed# — bug fix

Format notes:
  - Use [discrete] before ==== headings inside table cells to suppress TOC entries.
  - Each JIRA reference appears in parentheses at the end: (SCAL-XXXXXX)
  - Use `*` bold for version labels and metadata lines inside cells.

== New features

[.release-notes-table, cols="4,1"]
|===
| Description | Feature category

a|
Pin and unpin Spotter conversations from the chat sidebar, with custom
pin/unpin labels, via `SpotterChatPinConfig` (`spotterChatPinConfig` on
`SpotterSidebarViewConfig`).

*Doc reference*: xref:<page>.adoc[Pin Spotter conversations]
| Spotter

a|
Customize Spotter starter-prompt categories (Quick Search, Deep Analysis, and
Data Literacy) with your own labels and questions via `StarterPromptsConfig`.
Toggle individual prompt pills with `Action.QuickSearchPill`,
`Action.DeepAnalysisPill`, and `Action.DataLiteracyPill`. Also opens the
Spotter chat panel automatically when a Liveboard loads, via
`openSpotterOnLiveboardByDefault` (default `true`); adds Liveboard-specific
starter prompts through `StarterPromptsConfig.liveboard`; and lets you pin a
`SpotterEmbed` to a single analyst with `SpotterAnalystConfig`.

*Doc reference*: xref:<page>.adoc[Configure Spotter starter prompts]
| Spotter

a|
Scope Liveboard filters and parameters to a specific tab or group using the
new `applicability` attribute, plus the new `HostEvent.GetGroups` and
`HostEvent.OpenParameter` events.

*Doc reference*: xref:<page>.adoc[Scope filters to a tab or group]
| Filters and parameters

a|
New `Action.EditInputTable` and `Action.AllLiveboardFilters` actions, and
`isScopedLiveboardFilteringEnabled` on `LiveboardAppEmbedViewConfig` to scope
filtering to a group of visualizations on a Liveboard.

*Doc reference*: <Add xref once this page is published>
| Liveboard
