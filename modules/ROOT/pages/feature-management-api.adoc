= Feature delegation APIs
:toc: true
:toclevels: 2

:page-title: Feature delegation APIs
:page-pageid: feature-management
:page-description: Search feature configurations, assign features to Orgs, and set feature values using the REST API
:keywords: feature delegation, feature management, feature assignment, feature value, Org features, REST API

The feature delegation API lets ThoughtSpot Cluster and Org admins retrieve feature configurations, assign features to Orgs, and set feature values programmatically. These endpoints replicate the feature delegation capabilities available in the link:https://docs.thoughtspot.com/cloud/latest/admin-portal-2#_feature_management[new Admin portal UI, window=_blank].

ThoughtSpot provides public REST API v2 endpoints for the following purposes:

* To search the feature configurations available on your instance at the Cluster or Org scope.
* To assign features to Orgs, or remove Org assignments.
* To set feature values at the Cluster or Org scope, and reset Org-level overrides.

All endpoints are under `/api/rest/2.0/configurations/features/` and are available from ThoughtSpot Cloud 26.10.0.cl.

== Required privileges
All feature delegation API endpoints require the `ADMINISTRATION` or `ORG_ADMINISTRATION` privilege. The `ORG_ADMINISTRATION` privilege applies only to Org admins. Some endpoints have additional restrictions, which are described in each endpoint section.

== Prerequisites

* Feature delegation is enabled on your ThoughtSpot instance.
* To set a feature value at `ORG` scope, the Org must be assigned to that feature. Otherwise, the API returns a `403` error. To assign Orgs to a feature, see <<update-feature-assignments,Updating feature assignments>>.

[#feature-scope]
== Feature scope
Feature configurations exist at two levels:

Cluster scope:: Global scope applicable at the instance level. Visible only to Cluster administrators. Returns `assigned_orgs` and `is_org_aware` for each feature, and `feature_value` for features that are not Org-aware.
Org scope:: A per-Org value override, visible to Org admins. Returns `element_type`, `element_config`, and `element_value` for each feature.

== Feature identifiers

Each feature can be referenced by its:

* `feature_name`: a human-readable name, such as `index_columns`.
* `feature_id`: the underlying system identifier, such as `feature.search.columnIndexing`.

Both forms are accepted in requests to any endpoint that takes a `feature_identifier`.

NOTE: The format of `feature_id` is internal and can change without notice. Use `feature_name` as the stable identifier in your integrations where possible.

== Feature categories

Features are grouped into availability categories:

* `GENERAL_ACCESS`: Generally available features. This is the default.
* `EARLY_ACCESS`: Features marked for early access.

[#search-features]
== Searching features
The `/api/rest/2.0/configurations/features/search` API endpoint returns the feature configurations available on the ThoughtSpot instance. Use this endpoint to view which features are available, which Orgs a feature is assigned to, and the current feature values for an Org.

Requires the `ADMINISTRATION` or `ORG_ADMINISTRATION` privilege. Org admins with the `ORG_ADMINISTRATION` privilege can call this endpoint only with `scope` set to `ORG`.

=== Request parameters
[cols="2,4", options="header"]
|===
|Parameter | Description
| `scope`
|__String__. Scope of the search. Valid values are:

* `CLUSTER`: Returns the Cluster-admin view, including `assigned_orgs` for each feature. Requires the `ADMINISTRATION` privilege.
* `ORG`: Returns the Org-admin view, including `element_value` for each feature.

| `org_identifier`
|__Integer__. Numeric ID of the Org to scope the search to. Required when `scope` is `ORG`. Ignored when `scope` is `CLUSTER`.

| `category`
|__String__. Optional. Feature availability category. Valid values are `GENERAL_ACCESS` (default) and `EARLY_ACCESS`.
|===

=== Example request

Searching features with Cluster scope::
[source,cURL]
----
curl -X POST \
  --url 'https://{ThoughtSpot-Host}/api/rest/2.0/configurations/features/search'  \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer {AUTH_TOKEN}' \
  --data-raw '{
  "scope": "CLUSTER",
  "category": "GENERAL_ACCESS"
}'
----

Searching features at Org scope::
[source,cURL]
----
curl -X POST \
  --url 'https://{ThoughtSpot-Host}/api/rest/2.0/configurations/features/search'  \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer {AUTH_TOKEN}' \
  --data-raw '{
  "scope": "ORG",
  "org_identifier": 1,
  "category": "GENERAL_ACCESS"
}'
----

=== Example response
If the API request is successful, the API returns `200 OK` and an array of feature groups. The fields returned for each feature depend on the `scope` of the request. For more information, see <<feature-scope,Feature scope>>.

Global view::
[source,JSON]
----
[
  {
    "feature_group": "search",
    "docs_url": null,
    "features": [
      {
        "feature_id": "feature.search.columnIndexing",
        "feature_name": "index_columns",
        "assigned_orgs": [
          {
            "org_id": 0,
            "org_name": "Primary"
          }
        ],
        "is_org_aware": true,
        "feature_value": null,
        "docs_url": null
      }
    ]
  }
]
----

Org-specific view::
[source,JSON]
----
[
  {
    "feature_group": "spotter",
    "docs_url": null,
    "features": [
      {
        "feature_id": "feature.spotter.liveboardAssist",
        "feature_name": "spotter_on_liveboard",
        "assigned_orgs": null,
        "is_org_aware": null,
        "feature_value": null,
        "element_type": "toggle",
        "element_config": null,
        "element_value": "true",
        "docs_url": null
      }
    ]
  },
  {
    "feature_group": "downloads",
    "docs_url": null,
    "features": [
      {
        "feature_id": "feature.export.fileInstructions",
        "feature_name": "downloaded_file_instructions",
        "assigned_orgs": null,
        "is_org_aware": null,
        "feature_value": null,
        "element_type": "input",
        "element_config": {
          "type": "textarea"
        },
        "element_value": "Internal use only",
        "docs_url": null
      }
    ]
  }
]
----

=== Response parameters
[cols="2,4", options="header"]
|===
| Parameter | Description
| `feature_group`
| Name of the group that the features belong to, for example, `search` or `spotter`.

| `docs_url`
| Link to the documentation for the feature group or feature. `null` if no link is available.

| `features`
a| The features in the group. Each entry includes the following attributes:

* `feature_id`: System identifier of the feature, for example, `feature.search.columnIndexing`.
* `feature_name`: Human-readable name of the feature, for example, `index_columns`.
* `assigned_orgs`: The Orgs that the feature is assigned to, each with `org_id` and `org_name`. Returned for `CLUSTER` scope. `null` for `ORG` scope.
* `is_org_aware`: `true` when the feature supports per-Org values. Returned for `CLUSTER` scope. `null` for `ORG` scope.
* `feature_value`: Current Cluster-level value of the feature, as a string. For toggle features, the value is `"true"` or `"false"`. Returned for `CLUSTER` scope when the feature is not Org-aware. `null` for Org-aware features and for `ORG` scope. For `ORG` scope, use `element_value`.
* `element_type`: Type of control that represents the feature, for example, `toggle` or `input`. Returned for `ORG` scope.
* `element_config`: Configuration for the control. The structure varies by `element_type`; a `label` string is the most common attribute. For example, `{"type": "textarea"}` for a multi-line text input. `null` if there is no additional configuration. Returned for `ORG` scope.
* `element_value`: Current value of the feature for the Org, as a string. Returned for `ORG` scope.
* `docs_url`: Link to the documentation for the feature. `null` if no link is available.
|===

[#update-feature-assignments]
== Updating feature assignments
The `/api/rest/2.0/configurations/features/assignments/update` API endpoint updates the Org assignments for a feature. Use this endpoint to assign a feature to additional Orgs, unassign it from specific Orgs, or replace the full list of assigned Orgs.

Available to Cluster admins only. Org admins cannot call this endpoint. Requires the `ADMINISTRATION` privilege.

[CAUTION]
====
If you omit `operation`, the API uses `REPLACE`. Any Orgs currently assigned to the feature that are not in `org_identifiers` are unassigned. To add Orgs without affecting existing assignments, set `operation` to `ADD`.
====

=== Request parameters
[cols="2,4", options="header"]
|===
|Parameter | Description
| `feature_identifier`
|__String__. Feature name (`feature_name`) or feature ID (`feature_id`) of the feature to update.

| `org_identifiers`
|__Array of integers__. Numeric IDs of the Orgs to assign. Send an empty array with `operation` set to `REPLACE` to remove all Org assignments for this feature.

| `operation`
|__String__. Optional. Type of assignment update. Valid values are:

* `ADD`: Assigns the given Orgs in addition to existing assignments.
* `REMOVE`: Unassigns the given Orgs.
* `REPLACE`: Sets the assignment to exactly the given Orgs. This is the default.
|===

=== Example request

Adding Org assignments::
[source,cURL]
----
curl -X POST \
  --url 'https://{ThoughtSpot-Host}/api/rest/2.0/configurations/features/assignments/update'  \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer {AUTH_TOKEN}' \
  --data-raw '{
  "feature_identifier": "index_columns",
  "org_identifiers": [1, 2],
  "operation": "ADD"
}'
----

Removing all Org assignments::
[source,cURL]
----
curl -X POST \
  --url 'https://{ThoughtSpot-Host}/api/rest/2.0/configurations/features/assignments/update'  \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer {AUTH_TOKEN}' \
  --data-raw '{
  "feature_identifier": "index_columns",
  "org_identifiers": [],
  "operation": "REPLACE"
}'
----

=== Example response
If the API request is successful, the API returns `200 OK` and a `FeatureAssignmentResponse` object with the updated Org assignments.

Adding Org assignments::
[source,JSON]
----
{
  "feature_id": "feature.search.columnIndexing",
  "feature_name": "index_columns",
  "assigned_orgs": [
    { "org_id": 1, "org_name": "Acme" },
    { "org_id": 2, "org_name": "Beta" }
  ]
}
----

=== Response parameters
[cols="2,4", options="header"]
|===
| Parameter | Description
| `feature_id`
| System identifier of the feature, for example, `feature.search.columnIndexing`.

| `feature_name`
| Human-readable name of the feature, for example, `index_columns`.

| `assigned_orgs`
a| The Orgs that the feature is assigned to after the update. Each entry includes the following attributes:

* `org_id`: Numeric ID of the Org.
* `org_name`: Name of the Org.
|===

[#update-feature-values]
== Updating feature values
The `/api/rest/2.0/configurations/features/values/update` API endpoint sets the value of a feature at the Cluster or Org scope. Use this endpoint to set a per-Org value override, or to set the Cluster-level value for a feature.

Requires the `ADMINISTRATION` or `ORG_ADMINISTRATION` privilege. The `ORG_ADMINISTRATION` privilege applies only to Org admins.

[WARNING]
====
Setting `reset_org_overrides` to `true` at `CLUSTER` scope removes all per-Org value overrides for this feature. All Orgs then inherit the new Cluster-level value. This operation cannot be undone through the API.
====

=== Request parameters
[cols="2,4", options="header"]
|===
|Parameter | Description
| `scope`
|__String__. Scope at which to set the value: `CLUSTER` or `ORG`.

| `org_identifier`
|__Integer__. Numeric ID of the Org for which to set the value. Required when `scope` is `ORG`. Ignored when `scope` is `CLUSTER`.

| `feature_identifier`
|__String__. Feature name (`feature_name`) or feature ID (`feature_id`) of the feature to update.

| `feature_value`
|__String__. New value to assign to the feature, as a string. For toggle features, use `"true"` or `"false"`.

| `reset_org_overrides`
|__Boolean__. Applicable only when `scope` is `CLUSTER`. Required when `scope` is `CLUSTER` for an Org-aware feature. Must be omitted when `scope` is `ORG`; passing it at `ORG` scope returns a `400` error.

* When set to `true`, any existing per-Org value overrides for this feature are also removed so that all Orgs inherit the new Cluster-level value.
* When set to `false`, existing per-Org value overrides are retained.
|===

=== Example request

Setting an Org-level override::
[source,cURL]
----
curl -X POST \
  --url 'https://{ThoughtSpot-Host}/api/rest/2.0/configurations/features/values/update'  \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer {AUTH_TOKEN}' \
  --data-raw '{
  "scope": "ORG",
  "org_identifier": 1,
  "feature_identifier": "index_columns",
  "feature_value": "true"
}'
----

Setting the Cluster value and reset all Org overrides::
[source,cURL]
----
curl -X POST \
  --url 'https://{ThoughtSpot-Host}/api/rest/2.0/configurations/features/values/update'  \
  -H 'Accept: application/json' \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer {AUTH_TOKEN}' \
  --data-raw '{
  "scope": "CLUSTER",
  "feature_identifier": "index_columns",
  "feature_value": "true",
  "reset_org_overrides": true
}'
----

=== Example response
If the API request is successful, the API returns `200 OK` and a `FeatureValueResponse` object with the updated feature value.

[source,JSON]
----
{
  "feature_id": "feature.search.columnIndexing",
  "feature_name": "index_columns",
  "feature_value": "true"
}
----

=== Response parameters
[cols="2,4", options="header"]
|===
| Parameter | Description
| `feature_id`
| System identifier of the feature, for example, `feature.search.columnIndexing`.

| `feature_name`
| Human-readable name of the feature, for example, `index_columns`.

| `feature_value`
| The value of the feature after the update, as a string.
|===
